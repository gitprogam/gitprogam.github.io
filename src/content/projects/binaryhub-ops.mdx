## 왜 직접 돌리냐면

[북곽툴즈](/projects/nsgh-tools/), [StudyAce](/projects/studyace/), [BBlog](/projects/bblog/)는 전부 `binaryhub.club` 밑에서 돌아가요. 클라우드 서버를 빌린 게 아니라, 동아리가 관리하는 PC 한 대에서 직접 돌리고 있어요.

그렇다고 전부 한곳에 몰아넣진 않았어요. 사이트마다 성격 보고 어디에 둘지 따로 정했어요.

- 저장할 것도 서버 기능도 없는 정적 사이트(무쓸모.앱)는 Cloudflare Pages 에 올렸어요. 서버가 할 일이 없는데 PC 자원을 쓸 이유가 없으니까요. 옮기고 나서 PC 메모리도 250MB 정도 아꼈어요.
- DB 랑 API 위주의 작은 앱(StudyAce 첫 버전)은 Cloudflare Workers + D1 로 시작했어요.
- 서버에서 페이지 그리고, 파일이랑 비밀값을 다루는 앱(북곽툴즈, 부원 블로그)은 PC 에 뒀어요. 클라우드로 옮기는 것도 고민했는데, 부원 글 저장이랑 이미지 업로드 흐름을 통째로 다시 짜야 하고 비밀값이랑 디버깅이 여기저기 흩어지는 게 더 손해라고 봤어요.

PC 에서는 바깥에서 들어올 수 있는 포트를 하나도 안 열어 놨어요. 대신 Cloudflare Tunnel 이 PC 쪽에서 Cloudflare 로 먼저 연결을 걸어 두고, 들어오는 요청을 그 연결로 받아 와요. 공유기 포트포워딩도, 공인 IP 도 필요 없고 PC 주소도 밖에 안 드러나요. HTTPS 인증서는 Cloudflare 가 알아서 해 주고요.

터널은 모든 요청을 PC 안의 프록시(Caddy) 하나로 보내고, 어느 서비스로 갈지는 Caddy 가 주소랑 경로를 보고 정해요. 그래서 서비스를 새로 붙이거나 경로를 바꿀 때 터널은 안 건드리고 Caddy 설정만 고치면 돼요. Caddy 는 설정 바꿔도 껐다 켤 필요 없이 바로 반영돼서 이 역할에 딱이었어요.

직접 만든 Next.js 앱들은 컨테이너 없이 PM2 로 띄우고, Ghost 처럼 가져다 쓰는 건 Docker 로 띄워요.

## 배포 중에도 안 끊기게

앱마다 똑같은 걸 두 벌(blue/green) 준비해 두고, 빌드 결과물도 따로 둬요. 배포 스크립트는 이렇게 돌아가요.

1. 지금 안 쓰는 쪽에서 새 버전을 빌드해요. 빌드가 실패하면 여기서 멈추고, 돌고 있는 쪽은 안 건드려요.
2. 새 버전을 띄우고 응답이 올 때까지 기다려요.
3. Caddy 가 가리키는 쪽을 새 버전으로 바꾸고 설정을 다시 읽게 해요.
4. 밖에서 들어오는 것처럼 요청을 보내 봐요. 실패하면 Caddy 설정을 원래대로 되돌려요.
5. 옛 버전은 안 지우고 멈춰만 둬요. 문제 생기면 가리키는 쪽만 다시 바꾸면 끝이에요.

## 세 개가 한꺼번에 꺼진 날

어느 날 Cloudflare 위에서 따로 도는 것만 빼고 사이트 전부가 530 오류를 내고 있었어요. 확인해 보니 앱은 멀쩡한데 앞단의 터널, 프록시, Docker 가 동시에 꺼져 있더라구요. 셋 다 터미널에서 손으로 띄워 둔 거라, 죽으면 다시 살려 줄 게 아무것도 없었어요... 그때 "부팅할 때 켜기"랑 "죽으면 되살리기"가 완전히 다른 문제라는 걸 알았어요.

그래서 5분마다 도는 감시 스크립트를 만들었어요. 프록시가 요청을 안 받고 있으면 설정 파일이 멀쩡한지부터 검사하고 다시 띄워요. 설정이 깨진 채로 무작정 다시 띄우면 똑같이 또 죽을 뿐이니까요. 터널이랑 Docker 도 같은 식으로 봐요. 만들고 나서는 터널을 일부러 두 번 꺼 보고 진짜 살아나는지까지 확인했어요. 안 돌려 본 감시 장치는 없는 거나 마찬가지라서요.

## http 도 열려 있었다

검색 콘솔에 `http://` 주소가 따로 잡혀 있길래 봤더니, 모든 사이트가 암호화 안 된 http 로도 그냥 열리고 있었어요 ㅋㅋ Cloudflare 가 http 요청도 터널로 그대로 넘기는데, 프록시 쪽에서 그걸 구분을 안 하고 있었던 거예요. 접근 로그를 켜 보니 Cloudflare 가 원래 프로토콜을 `X-Forwarded-Proto` 헤더에 담아 보내 주고 있었어요. 그래서 이 값이 http 면 https 로 301 시키게 했어요. 로그를 안 켜 놨으면 원인을 못 찾았을 거예요.

## 메모를 믿었다가

운영 메모에는 "robots.txt 는 Cloudflare Worker 가 대신 응답한다"고 적혀 있었어요. 근데 실제 응답 헤더를 보니까 프록시랑 앱이 응답하고 있었고, Worker 설정은 파일에만 남아 있었어요. 그 뒤로는 어디서 응답하는지를 메모 말고 헤더로 매번 확인해요.

## 손으로 뜬 백업 34개

프록시 설정 파일 옆에 손으로 복사해 둔 백업 파일이 34개나 쌓여 있었어요. 설정 파일을 git 으로 관리 안 하고 있어서 그랬던 거라, 이참에 git 으로 넣었어요. 정리하다 보니 주석이 실제 설정이랑 다르게 적혀 있던 데도 찾았고요.
